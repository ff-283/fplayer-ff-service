## 一、高频必问：架构设计

### Q1: "这个项目的整体架构是什么？讲一下数据流"

**回答框架**：三端架构 + 控制面/数据面分离

```
桌面端 (C++) ──RTMP推流──→ ZLMediaKit ──HTTP-FLV/HLS──→ 移动端 (Flutter)
    │                            ↑                            │
    └─── REST API ──→ Gateway (Go) ←─── REST API ────────────┘
                      控制面 (会话管理/地址编排)
```

**关键话术**：
- "控制面用 Go 写了一个 Gateway（[gateway/main.go:1-860](gateway/main.go)），管理流会话、做 IP 可达性探测、地址编排"
- "数据面用 ZLMediaKit 做协议转换，RTMP 推进去自动出 HLS/HTTP-FLV/RTSP，一端推流全协议分发"
- "分离设计的好处：Gateway 挂了不影响正在推的流，ZLM 照常分发"

### Q2: "为什么用 Go 写 Gateway，不用 Node.js？"

- Go 编译为单二进制，部署简单（[gateway/main.go](gateway/main.go) 零外部依赖，仅用 net/http 标准库）
- 内存会话管理（sync.RWMutex），比 Node.js 的 GC 可控
- 配合 kernel-console（[kernel-console/main.go](kernel-console/main.go)）做无头部署，一个 exe 搞定

### Q3: "你这个项目的分层设计是怎么想的？"

```
app/          → 入口 (main.cpp)
widget/       → UI 层 (CaptureWindow)
service/      → 业务编排层 (工厂模式)
runtime/      → 运行时工厂 (后端切换)
backend/      → 后端实现 (FFmpeg/Qt6/DXGI)
api/          → 抽象接口层 (纯虚类)
common/       → 公用工具 (OpenGL渲染器)
```

"依赖方向是 app → widget → service → runtime → backend → api，上层不依赖具体实现，通过 api/ 的纯虚接口解耦。"

## 二、C++ 音视频核心

### Q4: "FFmpeg 播放器的线程模型是怎样的？"

📍 代码：[backend/media_ffmpeg/playerffmpeg.cpp](https://github.com) 约 1265 行

**三线程架构**：
1. **解复用线程 (demux)**：`av_read_frame()` 读包 → 按 stream_index 分别 push 到视频/音频 packet queue
2. **解码线程 (decode)**：从 packet queue 取包 → `avcodec_send_packet` / `avcodec_receive_frame` → YUV frame → push 到 frame queue
3. **音频线程 (audio)**：从解码后的音频 frame queue 取 → `swr_convert` 重采样 → Qt `QAudioSink` 输出

**关键细节**：
- 音视频同步：PTS 时间戳，以音频时钟为主时钟，视频帧根据 PTS 决定 sleep 或 drop
- 格式转换：非 YUV420P 格式通过 `sws_scale` 转为 YUV420P（为 OpenGL 渲染做准备）
- Seek：`avformat_seek_file` + 刷新编解码器缓冲区
- EOF 循环：播放到末尾自动从头重启

### Q5: "怎么处理音视频同步的？"

1. 音频线程每输出一帧，更新 `audio_clock`（基于 PTS + 已播放样本数/采样率）
2. 视频帧解码后读取其 PTS，与 `audio_clock` 比较：
   - 视频超前 → sleep（计算差值，精确到毫秒）
   - 视频落后 → 立即渲染（丢帧策略防止延迟累积）
3. 使用音频为主时钟的原因：人耳对音频不连续更敏感

### Q6: "为什么要把非 YUV420P 的帧转成 YUV420P？"

- OpenGL 渲染需要统一格式，YUV420P 是三平面格式（Y/U/V 分离），纹理上传效率高
- YUV420P → RGB 转换在 GPU 侧 shader 完成，比 CPU 转省带宽
- OpenGL 纹理可以用 3 个 sampler2D 分别绑定 Y/U/V 平面

📍 渲染器：[common/fglwidget.cpp](common/src/fglwidget.cpp)（OpenGL YUV 渲染器，双缓冲 PBO）

### Q7: "硬编码是怎么支持的？"

📍 [backend/stream_ffmpeg/streamffmpeg.cpp](backend/stream_ffmpeg/src/streamffmpeg.cpp)

- **NVENC**（NVIDIA）：`h264_nvenc` / `hevc_nvenc`
- **AMF**（AMD）：`h264_amf` / `hevc_amf`
- **QSV**（Intel）：`h264_qsv` / `hevc_qsv`
- **MediaFoundation**（Windows 通用）：`h264_mf`
- 软编码回退：`libx264`

选择策略：先检测 GPU 设备 → 优先同厂商硬编 → 无 GPU 回退软编 → 码率基于 BPP 模型自动估算

### Q8: "屏幕捕获怎么实现的？"

两种方案，可切换：
1. **FFmpeg gdigrab**：[backend/media_ffmpeg/screencaptureffmpeg.cpp]() — 兼容性好，性能一般
2. **DXGI Desktop Duplication**：[backend/desktopcapture_dxgi/]() — Windows 原生，低延迟，支持 GPU 直出

DXGI 方案优势：直接从 GPU 显存获取桌面帧，无需 CPU 拷贝，延迟比 gdigrab 低 80%+

## 三、流媒体协议

### Q9: "RTMP、HTTP-FLV、HLS 的区别？为什么你的项目三种都支持？"

| 协议 | 延迟 | 兼容性 | 适用场景 |
|------|------|--------|----------|
| RTMP | 1-3s | Flash 时代，H5 不支持 | 推流端（OBS/ffmpeg 生态好） |
| HTTP-FLV | 1-3s | H5 需 MSE/flv.js | Web 低延迟播放 |
| HLS | 5-15s | 全平台原生支持 | 移动端/Web 通用播放 |

**设计逻辑**：
- RTMP 做**推流入口**（桌面端 OBS/FFmpeg 生态成熟）
- ZLMediaKit 自动转封装 → HTTP-FLV（低延迟 Web 播放）+ HLS（iOS/Safari/微信内置浏览器）
- 三种输出共存，客户端按能力选（移动端 HTTP-FLV 不可用时自动切 HLS）

### Q10: "延迟能做到多少？瓶颈在哪？"

- **端到端延迟**：局域网 1-3s（HTTP-FLV 模式），公网 2-5s
- HLS 延迟较高是因为分片策略（2s/段 × 3 段 = 最少 6s 缓冲），可调但牺牲稳定性
- 瓶颈：编码延迟 > 网络传输 > 播放缓冲
  - 编码：使用硬件编码器（NVENC ~10ms/frame）vs 软编码（x264 ultra fast ~30ms/frame）
  - 传输：局域网 RTMP over TCP 几乎无延迟
  - 缓冲：播放器的 jitter buffer / GOP 大小决定起播延迟
- 低延迟方案：WebRTC（<500ms），但移动端兼容性差，项目中 ZLM 已配置 WebRTC 但桌面/移动端暂时未启用

### Q11: "你的公网模式是怎么实现的？"

📍 [gateway/main.go](gateway/main.go) — `publicHostOverride` / `publishHostForResponse()`

**问题**：服务在内网（192.168.x.x），外网客户端需要公网 IP
**方案**：
1. Gateway 接受 `publicHost` 参数（通过 API 或环境变量）
2. 地址编排时，如果启用了公网代理，返回的推流/播放 URL 中的 host 替换为公网 IP/域名
3. FRP（Fast Reverse Proxy）做端口映射：公网 1935 → 内网 1935

```
外网客户端 → frp公网IP:1935 → FRP隧道 → 内网ZLM:1935
              ↑                      ↑
           publicHost覆盖        实际服务在内网
```

## 四、工程能力

### Q12: "为什么你的桌面端主窗口 6746 行？不觉得太长了吗？"

"CaptureWindow 确实偏长，因为它承担了四种模式（摄像头/屏幕/文件/合成）的所有 UI 逻辑 + 推流拉流控制 + AI 对话框 + 截图库侧栏。当时为了快速迭代，先在一个文件里实现完整功能。如果要重构，会拆成：
- `CaptureWindow` — 主框架 + 模式切换
- `CameraModeController` / `ScreenModeController` / `FileModeController` / `ComposeModeController` — 各模式逻辑
- `StreamingPanel` — 推流/拉流独立面板
- `AiChatPanel` — AI 对话独立组件"

**加分回答**：实际上 Service 层（[service/](service/)）已经用工厂模式解耦了业务逻辑，UI 层的臃肿是时间问题不是设计问题。

### Q13: "CMake 工程的结构是怎么组织的？怎么管理第三方依赖？"

📍 [CMakeLists.txt](CMakeLists.txt) + [cmake/3rd.cmake](cmake/3rd.cmake) + [cmake/utils.cmake](cmake/utils.cmake)

- 自定义 `add_standard_module` 宏：统一处理 AUTOMOC/AUTOUIC/AUTORCC + src/include/private/uis/res 目录结构 + 导出符号
- 第三方依赖管理：
  - **FFmpeg**：预编译库，根据编译器（MSVC/MinGW/GCC）自动选择 lib 路径
  - **Logger/yaml-tool**：通过 CPM.cmake 从 Git 拉取
  - Qt6：通过 CMake find_package
- 构建选项开关：`FPLAYER_BUILD_MEDIA_FFMPEG`、`FPLAYER_BUILD_STREAM_FFMPEG`、`FPLAYER_BUILD_MEDIA_QT6` 等，可按需裁剪
- CPack 打包：NSIS (Windows) + DEB/TGZ (Linux) + 自动下载 VC++ 运行时

### Q14: "你是怎么做多平台支持的？"

| 组件 | Windows | Linux |
|------|---------|-------|
| 桌面端 | MSVC/MinGW + Qt6 | GCC + Qt6 |
| 服务端 | PowerShell 脚本 + .bat | Bash 脚本 + systemd |
| 移动端 | — | Android build |

- 桌面端 CMake 自动检测编译器 + 平台，选择正确的 FFmpeg 库路径
- 屏幕捕获自动切换：Windows → DXGI/gdigrab，Linux → X11/xdg-desktop-portal
- 服务端启动脚本：PowerShell 和 Bash 两份实现，功能等价（端口探测→INI 补丁→进程启动→健康检查）
- 公网主机选择：Linux 版 Gateway 会做 IP 可达性探测（连客户端 IP 的 53 端口确定源接口），Windows 版简化为直接选本机 IP

### Q15: "你做了哪些错误处理和容错？"

1. **端口冲突处理**：动态端口探测（[scripts/start-all.ps1:1-234](scripts/start-all.ps1)）— 优先常用端口，被占用则随机 → ZLM INI 动态补丁
2. **健康检查重试**：Gateway 启动后轮询 `/healthz`，最多重试 8 次（[gateway/main.go](gateway/main.go) + [kernel-console/main.go](kernel-console/main.go)）
3. **优雅关闭**：退出时按顺序终止子进程（UI→Gateway→ZLM），1.5 秒超时后强制 kill
4. **播放器 EOF 处理**：文件播放到末尾自动从头循环
5. **API 幂等**：同 app+stream 名称重复调用 start 不创建重复会话，直接返回已有

## 五、移动端 (Flutter)

### Q16: "Flutter 移动端主要做了什么？"

- 单页播放器 [lib/main.dart](https://github.com) 1431 行
- 双模式输入：服务模式（Gateway API 解析 URL）+ 直连模式（手动输入 URL）
- media_kit（libmpv 封装）支持 HLS/HTTP-FLV/RTMP
- 平台自适应：Web/Android 默认 HLS，Windows 默认 HTTP-FLV
- 设置持久化（SharedPreferences）
- 日志系统（200 条上限，按级别着色）
- Material 3 深/浅色主题

### Q17: "为什么不直接用 video_player 官方插件？"

- `video_player` 不支持 RTMP 和 HTTP-FLV（只支持 HLS/DASH/MP4）
- `media_kit` 底层是 libmpv，协议支持全（HLS/FLV/RTMP/RTSP 都行）
- libmpv 解码性能好（硬件解码），适合直播场景
- 代价：包体积增大 ~15MB（libmpv native libs）

## 六、可能的追问陷阱

### Q18: "这个项目有什么不足？如果重来会怎么做？"

**诚实 + 改进方向**（面试官喜欢能自我批判的候选人）：
1. Gateway 无鉴权 → 应该加 JWT/Basic Auth
2. 流会话仅内存 → 重启丢失，应该加持久化或至少 Redis
3. 无性能测试数据 → 应该做压测（并发路数、内存/CPU 曲线）
4. 移动端代码单文件 → 应该拆组件 + 状态管理（Provider/Riverpod）
5. 无 CI/CD → 应该加 GitHub Actions 自动构建 + 测试
6. 无单元测试覆盖 → 桌面端应该加 FFmpeg 后端 mock 测试

### Q19: "如果有 1000 路并发推流，你的系统会出什么问题？"

1. **Gateway 内存**：每个 streamRecord 约 1KB，1000 路 = 1MB — 不是问题
2. **ZLM 性能**：瓶颈在编解码，单实例通常支持几十路，1000 路需要集群 + 转码节点分离
3. **带宽**：1080p@30fps 约 4Mbps/路 → 1000 路 = 4Gbps 上行
4. **改进方向**：ZLM 集群 + 负载均衡 + Gateway 无状态化（可用 Nginx 反向代理多实例）

> 整个项目从 CMake 构建到跨平台打包脚本都是我独立完成，支持公网/局域网双模式部署。目前在持续迭代中。"
